# ДЗ 1. Рекомендательные теги в поиске

Продуктовый аналитик

# Идея

Сейчас теги в поиске работают как фильтры: для "платья" показывают "красное платье", "вечернее платье". Но для широкого запроса вроде "для дома" лучше показать другие товары: "ножи", "вилки", "посуда". Это и есть рекомендательные теги. Нужно рассчитать A/B-тест и придумать правила, каким запросам их показывать.
Расчеты можно запустить в python (файл "dz.py")

## 1. A/B-тест
### Данные из задания
- DAU: 5000000
- 4 поиска на пользователя в день
- теги показываются в 60% поисков
- CTR сейчас 3%, хотим увидеть 3,3% (это +10%)
- alpha = 0,05, мощность = 0,8
- группы делятся по пользователям, тест максимум 14 дней

### Допущения
1. Подходящих запросов 6% (точной цифры нет, взято примерно). Проверка в части 3. Новые теги видят только они, поэтому выборка считается по ним
2. Пользователь заходит каждый день и ищет 4 раза. В жизни люди ходят реже, так что тест может набираться чуть медленнее
3. Поиски одного человека похожи друг на друга. Пусть корреляция rho = 0,05 (тоже взято примерно)
4. CTR стабильный, пользователи делятся случайно (по хешу user_id), перед тестом проводится A/A-тест

### Сколько нужно поисков
Формула для сравнения двух долей:

    n = (z(1-alpha/2) + z(1-beta))^2 * [p0(1-p0) + p1(1-p1)] / (p1 - p0)^2

Со значениями: z(0,975) = 1,96, z(0,8) = 0,84, p0 = 0,03, p1 = 0,033.

    n = 2,8^2 * (0,03*0,97 + 0,033*0,967) / 0,003^2 ~ 53200

Получается около 53200 подходящих поисков на каждую группу

### Поправка на пользователей
Делятся на группы пользователи, а не поиски, а поиски одного человека похожи друг на друга. Из-за этого выборку надо увеличить:

    DE = 1 + (m - 1) * rho

m это сколько подходящих поисков у одного человека за тест:
m = 4 * 0,6 * 0,06 * дни = 0,144 * дни

7 дней: m = 1,01, DE = 1, нужно 53200 поисков на группу, 105600 пользователей, это 2,1% от DAU
14 дней: m = 2,02, DE = 1,05, нужно 55900 поисков на группу, 55500 пользователей, это 1,11% от DAU

При 7 днях m почти равно 1, поэтому DE тоже почти 1
Пользователей на обе группы получается так: 2 * (поисков на группу) / m

### Итоговый выбор
По условию тест идет не больше 14 дней и трафика надо трогать как можно меньше. Чем дольше тест, тем меньше пользователей нужно, поэтому выбрано 14 дней
По расчету нужно 1,11% пользователей. Итого 2% пользователей на 14 дней, чтобы был запас (rho и доля подходящих запросов взяты примерно)

- В тесте 100000 пользователей, по 50000 в каждой группе
- Подходящих поисков на группу 50000 * 2,02 = 100800, а нужно около 56 тысяч, так что запас есть
- Если подходящих запросов меньше 6%, пользователей надо больше: при 5% нужно 1,3%, при 4% нужно 1,6%, при 3% уже 2,1% и двух процентов не хватит. Поэтому долю подходящих запросов надо проверить до запуска

## 2. Правила отбора запросов
Запрос получает рекомендательные теги, если выполняются все три правила. Все считается по таблице пар "запрос -> следующий запрос" (для каждой пары видно, сколько уникальных пользователей ее сделали). Пороги пока стартовые, потом их можно подобрать по данным

Правило А. Люди расширяют запрос, а не уточняют
Берутся следующие запросы, которые ввели хотя бы 5 пользователей, и считается, в какой их доле есть текст первого запроса. Если эта доля меньше 0,4, правило выполнено
Например, после "платья" пишут "красное платье" (слово "платье" осталось), значит подходят фильтры. После "для дома" пишут "ножи", "посуда" (слов "для дома" нет), значит нужны рекомендации

Правило Б. Следующие запросы разные
- Разных следующих запросов (с >=5 пользователями) не меньше 20, чтобы точно набрать 10 тегов
- Нормированная энтропия H / log N не меньше 0,8. Это значит, что интересы людей разные и нет одного явного лидера

Правило В. Выдача широкая
В топ-100 товаров по запросу не меньше 15 разных категорий. Так отсеются редкие запросы, у которых разнообразие получилось случайно

## 3. Проверка до запуска теста
1. Метрики считаются по логам за две разные недели. Корреляция между неделями должна быть не меньше 0,9, иначе правило ловит шум
2. Ручная разметка 150-300 случайных запросов ("нужны рекомендации" или "нужны фильтры"). Точность (precision) правил должна быть не меньше 76%. Если меньше, пороги подбираются по максимуму F1
3. Оценка доли поиска, которую закрывают выбранные запросы. Это реальная доля вместо допущения в 6%. Ожидается 4-8%. Если получится меньше 4%, расчет надо повторить через dz.py

## 4. Итоги
- Нужно около 53200 подходящих поисков на группу, с поправкой на пользователей около 56 тысяч
- Тест: 2% пользователей, 14 дней, всего 100000 пользователей (по 50000 в группе)
- Правила: доля уточняющих запросов < 0,4, следующих запросов >= 20, энтропия >= 0,8, категорий в выдаче >= 15
